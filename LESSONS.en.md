### MIOT-017: An all-zero device state is neither a landing failure nor an external stop

- Scope: landing verification, external-stop polling, and the tail deadline in [songloft-org/songloft-plugin-miot#129](https://github.com/songloft-org/songloft-plugin-miot/issues/129); OH2 and similar Music API/proxy playback devices.
- Evidence: report on 2026-10-23: SongLoft v2.13.5 Docker + Nginx, plugin `2026.10.22.0`, LX source. The server returned HTTP 206 for playback, yet about 18 seconds later the log showed `Landing verify failed after 2 attempts: status=0, treating as unplayable and advancing` and the track switched. `player_get_play_status` kept returning `status/position/duration=0`; reading MIoT `siid=3, piid=1` directly also returned 0. Baseline `f65146c762a11000ce9a12866fbbc742e027de26` (v2026.10.22.0) accepted only `status===1` as a successful landing.
- Root cause: landing verification and external-stop polling both treated a successful query with an all-zero idle state as failure/stop evidence. That state proves neither failure nor a stop while the device is actually playing. Ignoring every idle sample is also wrong: real stops and source 404/5xx would then never advance.
- Rule and fix: enter the blind branch only for an idle sample from a stream dispatched by this process that has never reported a positive position or positive stream duration. Landing verification probes the current relative stream URL with HEAD: only an explicit 404/410/5xx marks it unplayable; a retrievable stream or an inconclusive probe (timeout, external URL, 405) is accepted after at most two attempts (first at 10 seconds, retry after 8 seconds) and left on the metadata timer. External-stop polling ignores these samples, except inside the hourly-chime window, which stays with smart recovery so an all-zero device can resume after the chime. The tail deadline advances on metadata without the extra thirty-second grace when the stream was dispatched more than sixty seconds ago, never reported a positive position, and still has all-zero media details; a freshly started stream keeps the grace. Any positive position or duration exits the blind branch immediately and restores the strict #124/#495 rules. Reloaded/adopted streams (`streamStartedAtMs=0`) have no dispatch time and do not enter the branch.
- Done right: uncommitted worktree, plugin baseline `f65146c`; parent read-only check at `cabfabbf` for the HEAD route and the "HEAD starts no live stream" tests. Eight new #129 regressions cover: a retrievable stream keeps playing with HEAD hitting `/api/v1/songs/16/play`; a 502 still advances; an inconclusive probe is accepted after two attempts; all-zero idle cannot confirm an external stop; a long blind stream advances at the metadata deadline; a fresh stream keeps the grace; a blind device advances through two natural transitions without blacklisting; OH2 Music API playback with all-zero status lands and advances twice. Running the new tests against old `f65146c` sources in a `git worktree` fails the first seven as expected; only the grace-preservation case passes. After the fix, `npx tsc --noEmit`, all 1264 tests, `npm run build`, and `npm run validate` pass. Existing hourly-resume, reload adoption, and #124/#495 cases remain green.
- Not run: real OH2 audio, reporter firmware/source, and long-running behavior; no parent code changes. If an older host does not support HEAD, the probe is inconclusive and the stream is still accepted after two attempts; whether a real device resumes reporting over time is unverified.
- Seen 1× (2026-10-23). Status: local implementation and automated verification complete; deployment, release, and hardware confirmation await separate authorization/records.

### MIOT-013: A tail idle sample must not discard the loop baseline of the same stream

- Scope: end-of-stream rewind detection for tracks with a normal duration, `observeTailLoop` and its two callers (deadline verification and tail probe); a recurrence of MIOT-007.
- Evidence: on 2026-10-20 the user supplied `songloft-logs-20261020-074137.zip`. Baseline before the fix: `85403abbdc07059caef75275a631cd545de53486` (v2026.10.20.1). `observeTailLoop` has not changed since `e0ad909` introduced it (`git log -S`), so three independent recurrences on 2026-10-16, 2026-10-19, and 2026-10-20 ran the same logic. On 10-20, at 07:40:48.615 the deadline check stored a tail baseline at stream position 182.1/182.212 seconds and deferred 161ms; at 07:40:50.113 the next sample reported `status=2` at the same 182.05-second position and the plugin logged `looped=false`; at 07:40:55.615 the device re-pulled the same URL and resumed at position 6.991 seconds, still `looped=false`, until the thirty-second grace or the user's manual next track at 07:41. On 10-16 the grace expired at 07:43:46 and advanced after roughly 32 seconds of replay; on 10-19 the two occurrences ended with a manual next and a user pause.
- Root cause: `observeTailLoop` treated every `status !== 1` sample as evidence of a stream change and cleared `tailLoopSample`. At natural completion the device often reports idle (0/2/3) once at the tail before re-pulling the same URL. The next playing sample arrives about five seconds later at position 6–7 seconds; with the baseline already gone, the adjacent-sample check cannot recognize the rewind and the plugin falls back to the thirty-second grace. MIOT-007's adjacent-sample window itself is valid; the gap was a status transition inside that window.
- Fix: keep the tail baseline across idle samples. For an idle sample at the tail of the same stream (stream-duration delta ≤1 second, position delta ≤2 seconds), advance only the sample timestamp so idle waiting is not counted as a long gap. Voice suspension, missing/invalid positions, foreign streams, and query failures still clear it. Regression covers both deadline verification and the tail probe.
- Done right: uncommitted worktree, Linux x86_64 / Node v26.3.0. Both new regressions fail as expected against isolated old `85403ab` sources (`the re-pulled stream must be recognized without the thirty-second grace`, `0 !== 1`), and pass after the fix together with all 1164 plugin tests, `npx tsc --noEmit`, `npm run build`, and `npm run validate`. Log evidence: `/tmp/songloft-logs-20261020/`; isolated old copy: `/tmp/miot-old-check/`.
- Rule: the status field is a sample snapshot, not stream-change evidence. Only explicit lifecycle events (pause, stop, repush, seek, new track, external takeover, query failure) may clear the tail rewind baseline. A rewind fix must verify both the deadline and tail-probe entry points and model the real shared-sampling cadence (tail playing → idle → rewind five seconds later); testing only two adjacent playing samples misses this path again.
- Not run: real-speaker audio, the problem audio, firmware model, and long-running behavior. No frontend or host changes; browser interaction and parent Go checks were not run. Whether the device re-pulls immediately after idle and where it resumes varies by firmware and still needs hardware confirmation.
- Seen 3× (2026-10-16, 2026-10-19, 2026-10-20); the 2026-10-15 MIOT-007 entry is the preceding event on the same path and is not counted again. Status: local fix and regression pass; deployment and hardware confirmation pending.

### MIOT-011: Strip model-independent fixed waits before blaming the model for slow AI chat

- Scope: the AI chat waiting hint and the interval between the two interrupt stop rounds, [songloft-org/songloft-plugin-miot#119](https://github.com/songloft-org/songloft-plugin-miot/issues/119).
- Evidence: on 2026-10-20, baseline `fb8b5ef56adc400fc2b6bcaa495c9952aceb9329`. In the reporter's [log](https://github.com/songloft-org/songloft-plugin-miot/issues/119#issuecomment-6281088024), `first_content_ms=1022` (T+5.41s) against `speech_dispatch_ms=9499` (T+13.89s): the model was not the bottleneck. Three model-independent fixed waits sat on the path: the three-second audible window of "收到，正在思考" still played even when the model had already finished during takeover; that window started only after the TTS cloud round-trip returned, stacking a full one-to-two-second round-trip on top; and the two interrupt stop rounds were separated by a fixed 2000ms. The dominant cause was the host's 500ms pump polling — see JSPLUG-001 in the [parent repository](https://github.com/songloft-org/songloft/blob/main/LESSONS.en.md). MIOT-010 recorded the "roughly 20-second delay" as unlocated; this entry is that localization.
- Rule and fix: skip the waiting hint entirely when generation has already completed by the end of takeover. Measure the hint's protection window from dispatch time and stop waiting once `remaining <= 0`. Both stop rounds remain unconditional; a status read-back does not replace the second round, because status 0/2 can be misreported ([songloft-org/songloft#449](https://github.com/songloft-org/songloft/issues/449)) and the read-back would perturb shared sampling and backoff. Only the inter-round interval shrinks, from 2000ms to the 600ms the firmware needs to settle. Diagnose this class of slowness by subtracting each fixed wait from the log first, and attribute to the model or network only afterwards.
- Done right: uncommitted worktree, Linux x86_64 / Node 26.5.0. 1150 plugin tests, `npx tsc --noEmit` (only the 6 pre-existing `HTTPStream` errors), the QuickJS build, and package validation pass; the `player_failures`/`player_status`/`player_transition`/`mina_status` regression matrix passes. Two new cases cover "no hint when the answer is ready before takeover" and "the protection window absorbs the cloud round-trip instead of extending past it". The window is based on `Date.now`, so tests must fake `setTimeout` and `Date` together to assert on its boundary; faking only `setTimeout` lets assertions drift with the real clock.
- Not run: the reporter's speaker model/firmware, actual audio, and long-running behavior. Whether 600ms is enough for the firmware to switch into media playback is inferred from logs and unverified on hardware.
- Seen 1× (2026-10-20). Status: lesson; real-device confirmation and release pending.
