# DLNA receiver

In the plugin's Settings → Devices → DLNA receiver, enter a name prefix and server LAN URL, select the desired speakers or groups, and save. **Both the master switch and each newly discovered target default to off.** A plugin receiver is advertised only when the master switch and target switch are on and the target is eligible. Disable plugin entries for speakers with native DLNA support to avoid duplicates; their native DLNA functionality is unaffected.

Each managed standalone speaker and eligible group has one entry named ‘prefix · speaker/group name’. Group members do not appear separately. A group requires at least two existing, managed speakers. Groups that do not meet these conditions remain visible with their switch and a specific reason, but are not advertised. This does not mean temporary device unreachability: offline errors are reported when controls actually fail. Empty and single-member groups do not have group receivers; their managed members remain standalone.

Device and group selections persist independently. A new group defaults to off without inheriting its members’ choices. Leaving a group restores each speaker’s previous choice; restoring the same group preserves its group selection. Turning off the master switch retains individual choices. Disabling one entry stops only playback it still owns and cannot affect another target or a new playlist that has taken ownership.

Standalone speakers and groups each have a persistent device ID and separate control paths, playback state, and event subscriptions. They can receive different music simultaneously without taking ownership from each other. A group’s identity is stored by group ID and survives renaming and membership changes. Receivers update when speakers are added, removed, unmanaged, or groups are edited or dissolved (within about 30 seconds in the background). Membership changes and dissolution drain pending cast commands and stop casting on the old members before updating targets. New members do not automatically continue the old media; cast again. Closing a receiver stops only playback it still owns and cannot stop a new playlist that has taken ownership.

Use an HTTP IPv4 URL reachable by the phone, computer, and speaker, such as `http://192.168.1.10:58091`. Subpath deployments may use `http://192.168.1.10:58091/music`. Search for the receiver name in a DLNA-capable sending app and cast MP3 music. For local phone files, the sending app must provide an accessible HTTP URL and remain online.

Discovery uses SSDP multicast on UDP `239.255.255.250:1900`. The server must be on the same LAN with multicast allowed; host networking is recommended for Linux Docker deployments. The host must include the accompanying HTTP peer address, UPnP extension method, and UDP address reuse changes. The settings page prompts for an upgrade on older hosts. All speakers share one SSDP socket and the Songloft HTTP port, without allocating a port per speaker. The plugin does not open an additional listener on port 8200. Sharing UDP port 1900 requires other listeners to allow address reuse too; binding failures appear as startup errors. When discovery fails alongside a NAS DLNA service, inspect startup errors and actual listening ports rather than inferring a plugin conflict from another project’s port 8200 setting.

Service URLs in the device description use paths starting with `/`, preserving the deployment subpath for senders that concatenate the server origin directly. Discovery advertisements still use a full HTTP URL for `LOCATION`. After updating the plugin, search for and select the receiver again in the sending app to avoid cached service URLs.

Play, pause, stop, and volume-setting commands are sent to all group members in parallel. Position, duration, and queried volume use the first speaker in the member list as reference. Parallel dispatch does not provide sample-level synchronization; network and firmware affect actual start times. Any explicit member failure returns a protocol error; partial play/resume failures attempt to stop the whole group. If any member requires a hard stop to pause, the entire group stops and subsequent playback starts from the beginning.

HTTP/HTTPS MP3 URLs are supported. URLs without a `.mp3` suffix require DIDL-Lite metadata declaring `audio/mpeg` or `audio/mp3`. Both escaped text and inline XML metadata sent by Flutter’s `dlna_dart` are accepted, preserving the original namespaces and entity encoding. The speaker fetches the original URL directly; the receiver does not import, download, or transcode media. Supported features include play, pause, stop, volume, media/position queries, and AVTransport, RenderingControl, and ConnectionManager event subscriptions. Position comes from the speaker and may remain zero if its firmware does not report it. When firmware ignores pause and requires a stop, the state becomes stopped and subsequent playback starts from the beginning. Seek, automatic next track, mute, and AirPlay are outside this first version.

Failed casting, play, pause, or stop actions display the action, UPnP error code, and reason on the settings page. All SOAP faults are also written to the backend log as `[DLNA] SOAP fault`, including the service, action, code, and protocol error reason, without media URLs or metadata. A subsequent "no media" fault does not replace the original casting error. Successful queries, stops, and unsupported capability probes do not clear the message either. A successful media submission, play action, or configuration save clears it.

External casting takes ownership only of the selected standalone speaker or group, disabling the previous playlist's automatic advancement and recovery polling. Starting a new playlist ends that ownership. Disabling the receiver stops playback it still owns, withdraws discovery advertisements, and releases sockets, timers, and subscriptions. It does not automatically resume the previous playlist.

`GET/PUT /api/v1/jsplugin/miot/receiver/config` is a JWT-protected management endpoint returning typed configuration and runtime status. Configuration fields are `enabled` (master switch), `enabled_ids` (selected target IDs, empty by default), `name` (prefix), and `base_url`. Preserve hidden member IDs returned by GET when saving so their choices survive leaving a group. Unknown target IDs return 400. The returned `receivers` array includes each receiver’s `id`, `account_id`, `device_id`, `name`, `group_id` (empty for standalone speakers), `members`, `enabled` (target switch), `available` (configuration eligibility), `running`, `state`, `error`, and media status. Targets come from managed devices rather than one selected `account_id/device_id` pair. Ineligible groups remain in `receivers` with `available=false` and an explanatory `error`, preserving their switch selection. Every receiver uses `/dlna/<id>/*` protocol paths. `/api/v1/jsplugin/miot/dlna/<id>/*` contains public LAN protocol endpoints that validate the TCP peer address supplied by the host. Do not expose these paths through a public reverse proxy. Event callbacks must use HTTP IPv4 URLs with the same IP as the subscribing TCP peer, and redirects are disabled.

Validation commands: backend `npx tsc --noEmit` and `node --test tests/dlna_receiver.test.mjs tests/player_failures.test.mjs tests/player_transition.test.mjs`; frontend `npm run typecheck`, `npm test`, and `npm run build`. Reachability from real sending devices and speakers, and firmware pause behavior, still require hardware validation.
